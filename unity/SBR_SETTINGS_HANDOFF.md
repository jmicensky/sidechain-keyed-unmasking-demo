# Handoff: SBR-matched dynamics settings for the Unity test sequence

Generated by `demo_engine/analysis/write_unity_sbr_handoff.py` from the sweep data; do not edit numbers by hand,
re-run `demo_engine/analysis/run_sbr_matched.sh` instead. For the Unity session working in `Modified_Johnson_Healy`.

## 1. What "best" means here

- **Metric:** Johnson & Healy (2024) speech-to-background ratio. SBR = speech-active RMS of the processed Dialogue
  group / RMS of the processed sum of the other four groups (Music, Background, Safety, Other), broadband, unweighted,
  both channels. "Speech-active" = 20 ms frames where the raw Dialogue stem is within 40 dB of its peak.
- **Targets:** HI +5.1 dB (J&H 95 % window 4.7 to 5.8 dB) and NH +12.2 dB (window 2.8 to 22.4 dB). Participants are
  mostly normal-hearing, so **NH is the primary target**; HI is the secondary condition.
- **One setting per mode and target, shared by all three test scenes** (Construction, Public Transit, Restaurant):
  the search minimizes the worst-scene |SBR - target|, then prefers the setting with the least gain reduction.
- **The SBR change comes from the dynamics only:** every makeup gain and the key gain are fixed at 0 dB.
- **Dialogue is compressed on purpose** in Group compression and Combined (ratio 2-4:1, mean gain reduction
  1.5-6 dB in every scene), for intelligibility; the background groups have to supply the SBR. Its effect is
  reported as Dialogue dynamic range (J&H Fig. 5 method: 99th minus 30th percentile of 125 ms window levels).
- **Search:** Latin Hypercube (800 / 1500 / 2000 points for Basic / Group / Combined) then an elitist local search
  per target, on the real stems. Data: `demo_engine/analysis/sbr_matched_*.csv`.

## 2. Which compressor the web test used, and how the values transfer to LL Dynamics

The web test used **neither JUCE nor the browser's `DynamicsCompressorNode`**. It used the demo_engine's own C++ DSP
(`demo_engine/include/*.h`) compiled to WebAssembly; the sweeps ran the same C++ natively. LL Dynamics shares the
gain curve but not the detector:

| | Web test (demo_engine) | LL Dynamics |
|---|---|---|
| Gain computer | soft knee, thesis Eq. 2 | identical |
| Detector input | mono (L+R)/2 | stereo-linked peak max(\|L\|,\|R\|) |
| Envelope | one-pole on the instantaneous **dB** level | one-pole on the **linear** peak, then dB |
| Look-ahead | none | none |
| Sidechain timing | sample-accurate | Priority -> Sidechain link, up to one block late |
| Max gain reduction | Basic ducking only | every mode |

LL Dynamics therefore reads the same signal several dB hotter, by an amount that depends on the material and the
time constants, so **web thresholds must not be copied across**. The transfer used here:

1. LL Dynamics was emulated offline (Compressor and Priority -> Sidechain paths). Checked against the real
   `LLDynamicsProcessor.cpp` on a real stem: max difference -168.6 dBFS, i.e. identical.
2. For each channel and scene, the LL Dynamics threshold that reproduces the web setting's **mean gain reduction**
   was solved (same ratio, knee, attack, release), then averaged over the three scenes.
3. One trim (dB) was applied so the LL Dynamics chain, with a 1024-sample sidechain lag (one block at Unity's
   current 1024 DSP buffer), lands on the target SBR. The trim moves the Sidechain threshold (Basic, Combined) or
   the four background Compressor thresholds (Group compression).

Section 4 gives the **LL Dynamics values to enter** (after step 3) and, for reference, the web values.

## 3. Input levels at the compressor inputs (web test)

power). LUFS is integrated loudness per ITU-R BS.1770-4. The Sidechain detector input is the Dialogue row.
**Playback/calibration level: none.** The web test had no SPL calibration; it played at whatever the listener's
system volume was. All levels and thresholds here are digital (dBFS), so Unity needs the offset (Delta) below.

**Delta for Unity:** for each mixer group, Delta = (level at that group's LL Dynamics input in Unity) - (the
matching web level above), using the **same measure** for both (speech-active RMS dBFS is closest to what the
detectors see; LUFS is fine if that is what Unity's tools report). Add Delta to that group's LL Dynamics
threshold. For the Sidechain effects, use the **Dialogue group's** Delta (their detector listens to Dialogue).

## 5. Calibrating in Unity

1. **Build the chain** for the mode (section 4 effect order, Priority Chan 1, Loudness Gate off, makeup 0).
2. **Measure Delta per group** (section 3) during a representative conversation, at each LL Dynamics input.
   Add Delta to that group's thresholds; Dialogue's Delta goes on every Sidechain threshold.
3. **Check gain reduction** with Meter IDs (`*_dynamics.csv`, mean/max per conversation) against the targets in
   section 4 (speech-active mean is the closest match to a conversation window). Nudge thresholds to match.
4. **Final check is SBR at the ear** (the planned Hagerman & Olofsson tool, Docs/CLAUDE_HANDOFF.md). If gain
   reduction matches but SBR is off, trust SBR: move the same trim the search used (Sidechain threshold for
   Unmasked / Combined, background Compressor thresholds for GroupCompress) until it hits the target.
5. **Then** apply the planned equal-loudness correction (A) across modes; it is a static gain on the whole mix, so
   it does not change SBR.

## 6. Caveats

- **Different material.** These settings were found on the demo scenes (Construction, Public Transit,
  Restaurant stems), not on the coffee-shop sentences and effects. Delta corrects level, not dynamics, so the gain
  reduction targets are a guide and the measured SBR is the deciding check.
- **Basic unmasking cannot hit one SBR in every scene.** Its gain follows Dialogue only, so scenes that start at
  different SBRs end at different SBRs (see the spread in its SBR tables). Group compression and Combined compress
  each background group on its own level and land much closer across scenes.
- **Sidechain lag.** LL Dynamics' Priority -> Sidechain link can be one DSP block late (21 ms at 1024). The trim
  assumes that worst case; a 256 buffer would make the ducking react sooner.
- **Class mapping.** Unity has four groups for the five web classes: Safety and Other both correspond to
  Randomized FX (the effects participants detect, the J&H "environmental sounds"); Background Noise and Music map
  directly. If both Safety and Other rows differ, use Safety's for Randomized FX (it is the closer analog).
- **SBR is a level metric.** It is the J&H operating point, not a measured intelligibility score.
